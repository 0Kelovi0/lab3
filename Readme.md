# Лабораторна робота: Розподілені обчислення з використанням бібліотеки MPI

Проєкт містить засоби автоматизованого розгортання віртуального обчислювального кластера на базі **Multipass + OpenMPI + NFS** та реалізації двох алгоритмів паралельного обчислення суми масиву розміром $N = 1\,000\,000\,000$ елементів мовою C із використанням стандарту **MPI (Message Passing Interface)**.

---

## 1. Архітектура та конфігурація кластера

* **Хост-машина:** Intel Core i5-11400H (6 ядер / 12 потоків), 16 ГБ ОЗП, Windows 11 (Hyper-V).
* **Топологія кластера:** 4 віртуальні вузли під керуванням Ubuntu 24.04 LTS (`manager`, `worker1`, `worker2`, `worker3`).
* **Ресурси кожного вузла:** 4 vCPU, 2560 МБ (2.5 ГБ) ОЗП, 10 ГБ диска (сумарно: **16 обчислювальних слотів**, **10 ГБ ОЗП**).
* **Мережева взаємодія:**
  * статичне зіставлення імен вузлів у `/etc/hosts`;
  * безпарольна автентифікація між усіма вузлами за протоколом **SSH**;
  * спільна мережева файлова система **NFS** (`/home/ubuntu/cloud`), змонтована з `manager` на всі робочі вузли для синхронного доступу до скомпільованих бінарних файлів;
  * конфігурація процесів у `/home/ubuntu/cloud/mpi_hosts` (`slots=4` на кожен вузол) із рівномірним розподілом процесів між вузлами (`--map-by node`).

---

## 2. Структура репозиторію

* `set_up_mpi.py` — скрипт автоматизованого створення віртуальних машин, встановлення `OpenMPI` та `NFS`, налаштування `/etc/hosts`, SSH-ключів і файлу `mpi_hosts`.
* `run_mpi.py` — утиліта для передачі вихідного коду на вузол `manager`, компіляції за допомогою `mpicc -O3` та запуску через `mpiexec` на кластері.
* `task1_mpi.c` — реалізація **Завдання 1** (рівномірний розподіл масиву на $10^9$ елементів типу `int` між процесами, локальне підсумовування та синхронна колективна редукція `MPI_Reduce` з операцією `MPI_SUM`).
* `task2_mpi.c` — реалізація **Завдання 2** (хвильове попарне згортання масиву на $10^9$ елементів типу `int64_t` за схемою *Controller–Workers* із прив'язкою обчислень до локальної пам'яті власника даних — *Data Locality*).
* `README.md` — опис проєкту, інструкції запуску та аналіз результатів.
* `prompts.md` — журнал запитів (промптів), використаних під час виконання роботи.

---

## 3. Інструкція з розгортання та запуску

### Крок 1. Розгортання MPI-кластера (4 вузли по 4 vCPU та 2.5 ГБ ОЗП)
```bash
python set_up_mpi.py 4 --cpu 4 --ram 2560
```

### Крок 2. Компіляція та запуск Завдання 1
```bash
python run_mpi.py --c task1_mpi.c
python run_mpi.py --r task1_mpi -n 16
```

### Крок 3. Компіляція та запуск Завдання 2
```bash
python run_mpi.py --c task2_mpi.c
python run_mpi.py --r task2_mpi -n 16
```

## 4. Результати експериментів

Усі вимірювання проведено для масиву розміром **$N = 1\,000\,000\,000$** елементів на 16 MPI-процесах (по 4 процеси на кожному з 4 вузлів кластера):

| Завдання | Файл та метод MPI | Кількість процесів | Очікуваний результат | Отриманий результат | Час виконання |
| :--- | :--- | :---: | :---: | :---: | :---: |
| **Завдання 1** | `task1_mpi.c` (`MPI_Reduce` + `MPI_SUM`) | 16 (4 вузли $\times$ 4) | `49500000000` | `49500000000` (`OK`) | **267.91 мс** |
| **Завдання 2** | `task2_mpi.c` (хвильове згортання, 30 хвиль, `Data Locality`) | 16 (1 контролер + 15 воркерів) | `5500000000` | `5500000000` (`OK`) | **11 663.44 мс** |

## 5. Висновки

1. **Ефективність розподіленої пам'яті:** На відміну від одновузлових багатопотокових реалізацій (Java/Go зі спільною пам'яттю), у моделі MPI кожен вузол виділяє пам'ять лише під свою частку масиву. Це дозволило обробити масив на $1\,000\,000\,000$ елементів ($\approx 7.45$ ГБ для `int64_t`) на віртуальних машинах із лімітом $2.5$ ГБ ОЗП на вузол без перевантаження пам'яті.
2. **Порівняння алгоритмів на кластері:**
   * **Завдання 1** демонструє високу швидкодію (**267.91 мс**), оскільки кожен процес незалежно підсумовує свою локальну ділянку, а по мережі передається лише 8 байт проміжної суми через деревоподібну колективну операцію `MPI_Reduce`.
   * **Завдання 2** потребує 30 послідовних хвиль синхронізації та міжвузлового обміну елементами правої половини масиву. Застосування принципу **Data Locality** (призначення контролером кожному воркеру виключно тих діапазонів лівої половини, які вже зберігаються в його локальній ОЗП) та рівномірного планування процесів (`--map-by node`) скоротило мережевий трафік у 3 рази та забезпечило стабільне виконання за **11.66 с**.
